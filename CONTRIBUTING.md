# Contributing to Rahi

Thanks for your interest in improving Rahi — an AI-powered career-guidance platform
for students. This guide explains how to set the project up locally, the conventions
we follow, and how to propose changes.

Rahi is an educational, student-focused project. Contributions of all sizes are
welcome: documentation fixes, bug reports, tests, accessibility improvements, and
new features that fit the roadmap (see [ROADMAP.md](ROADMAP.md)).

## Code of conduct

This project follows the [Contributor Covenant](CODE_OF_CONDUCT.md). By participating,
you agree to uphold it.

## Prerequisites

- **Node.js 22+** (the CI and the Docker image both run Node 22)
- **npm** (the repo uses `package-lock.json`; please don't switch package managers)
- Git

Everything else is optional. Rahi is designed to **run with no external services
configured** — see below.

## Local setup

```bash
git clone https://github.com/vaishnavi-eklaspur/rahi.git
cd rahi
npm install
cp .env.example .env.local   # optional — see "Environment variables"
npm run dev                  # http://localhost:3000
```

That's the whole setup. With an empty `.env.local` the app still runs: reports work via
URL encoding, the AI features show their deterministic fallback, and saved-report history
is disabled. Features light up as you add the matching environment variables.

## Environment variables

All variables are optional; add only the ones for the features you're working on.
See [`.env.example`](.env.example) for the full list.

| Variable | Enables |
|----------|---------|
| `DATABASE_URL` | Neon Postgres — short share links + saved-report history |
| `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` | Email login (generate a secret with `openssl rand -base64 32`) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | "Continue with Google" (register `<BETTER_AUTH_URL>/api/auth/callback/google` in Google Cloud) |
| `GEMINI_API_KEY` | Hosted AI narrative via Google Gemini |
| `OLLAMA_URL`, `OLLAMA_MODEL` | Local AI narrative via [Ollama](https://ollama.com) (no key needed) |

Never commit real secrets. `.env*` is git-ignored (except `.env.example`).

### Database schema (only if you work on DB-backed features)

The database is optional. If you want short links / history locally, point `DATABASE_URL`
at a Postgres database and create the schema:

- **Application table:** apply [`db/schema.sql`](db/schema.sql) (`psql "$DATABASE_URL" -f db/schema.sql`).
- **Auth tables:** generated by Better Auth — run `npx @better-auth/cli@latest migrate`.

## Development commands

| Command | What it does |
|---------|--------------|
| `npm run dev` | Start the dev server (Turbopack) at http://localhost:3000 |
| `npm run build` | Production build (type-checks as part of the build) |
| `npm run start` | Serve the production build |
| `npm run lint` | ESLint |
| `npm test` | Self-check (scoring/fusion/encoding) + Vitest suite (API validation, privacy, AI fallback) |
| `npm run test:unit` | Just the Vitest unit/integration suite (`tests/`) |
| `npm run test:e2e` | Playwright end-to-end tests |

## Reproducing CI locally

CI runs exactly these, and a failure blocks the merge:

```bash
npm ci
npm run lint
npm test
npm run build
npm run test:e2e
```

## Testing expectations

- The domain logic in `lib/` (scoring, fusion, sampling, encoding) is guarded by a
  framework-free self-check (`lib/riasec.selfcheck.ts`, run via `npm test`). If you
  change that logic, add or update an assertion there.
- API route handlers, report-ownership/privacy boundaries, and the AI fallback are
  covered by Vitest (`tests/`, run via `npm run test:unit`). Mock the database, auth,
  and LLM provider — tests must not need production credentials or a live network.
- User-facing flows are covered by Playwright (`e2e/`). If you change a flow, keep the
  e2e green and add a case for new behavior.
- Bug fixes should come with a regression check that would have caught the bug.

## Code quality

- TypeScript is strict — no `any` escape hatches without a clear reason.
- `npm run lint` and `npm run build` must pass before you open a PR.
- Keep changes focused; avoid unrelated refactors in the same PR.
- Don't log secrets or personal data.

## Branch naming

Use a short, prefixed branch name:

- `feat/<short-description>` — new feature
- `fix/<short-description>` — bug fix
- `docs/<short-description>` — documentation
- `chore/<short-description>` — tooling, CI, dependencies
- `test/<short-description>` — tests only

## Commit messages

- Write in the imperative mood: "Add aptitude edge-case test", not "Added…".
- Keep the subject line under ~72 characters; add a body explaining *why* when it isn't obvious.
- One logical change per commit where practical.

## Pull requests

Before opening a PR:

1. Branch off `main` and keep your branch up to date.
2. Make sure `npm run lint`, `npm test`, and `npm run build` all pass.
3. Fill in the PR template (what changed, why, how you tested it).
4. Link any related issue (e.g. `Closes #123`).
5. Note any user-facing or security-relevant impact.

A maintainer will review; please be responsive to feedback. Small, well-scoped PRs
are merged fastest.

## Reporting bugs

Open an issue using the **Bug report** template. Include steps to reproduce, what you
expected, what happened, and your environment (browser, OS, Node version).

## Proposing features

Open an issue using the **Feature request** template. Describe the problem you're
solving and who it helps before the solution, and check [ROADMAP.md](ROADMAP.md) to
see if it already fits a planned direction.

## Security

Please do **not** open public issues for security vulnerabilities. See
[SECURITY.md](SECURITY.md) for private reporting.
